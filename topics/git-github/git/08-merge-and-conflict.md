# Merge와 충돌 해결

별도 브랜치에서 작업을 마치면 그 변경을 기준 브랜치에 반영해야 함. `merge`는 지정한 브랜치의 이력을 현재 체크아웃한 브랜치에 통합함. 따라서 어느 브랜치에 서 있는지에 따라 결과가 달라짐.

## main에 작업 브랜치 합치기

실습에서는 작업 브랜치에 필요한 커밋을 만든 뒤 현재 상태를 정리하고 다음처럼 진행함.

```powershell
git switch main
git status
git merge docs/git-note
```

현재 `main`에 `docs/git-note`의 작업을 반영함. 작업 브랜치 자체가 자동 삭제되거나 그 이름의 위치가 바뀌는 것은 아님. 병합 후 파일과 이력을 함께 확인함.

## Fast-forward와 병합 커밋

![Fast-forward 병합](../assets/merge-fast-forward.svg)

`main`이 작업 브랜치의 이전 커밋을 가리키고 그 뒤에 작업 커밋이 이어져 있다면, `main`을 앞쪽 커밋으로 이동시켜 합칠 수 있음. 이를 fast-forward라고 하며 기본적으로 새 병합 커밋은 만들지 않음.

![병합 커밋](../assets/merge-commit.svg)

반면 분기 후 `main`과 작업 브랜치 양쪽에 각각 새로운 커밋이 있으면 한쪽 이름만 앞으로 옮겨 두 이력을 모두 표현하기 어려움. 이 경우 Git은 두 흐름을 잇는 병합 커밋을 만들 수 있음. 그림의 M은 두 부모를 가지며 두 작업 이력을 연결함.

양쪽에 각각 커밋이 있다는 것과 충돌이 생긴다는 것은 다름. 서로 다른 부분을 바꿨다면 Git이 자동으로 통합할 수 있음. 같은 부분을 서로 다르게 바꾸는 등 결과를 자동으로 결정할 수 없으면 충돌을 표시함.

## 충돌 표시를 읽고 최종 내용 정하기

`main`에서 작업 브랜치를 병합하다 같은 줄에서 충돌한 상황임.

```text
<<<<<<< HEAD
다음 공부: Git
=======
다음 공부: GitHub
>>>>>>> docs/git-note
```

`<<<<<<< HEAD` 아래는 현재 `main`의 내용, `=======` 아래는 합치려는 브랜치의 내용임. 개발자가 둘 중 하나를 선택하거나 둘을 조합해 최종 내용을 직접 정해야 함. 단순히 두 줄을 모두 남기는 것이 항상 올바른 해결은 아님.

VS Code의 Current Change는 현재 병합 대상 브랜치 쪽, Incoming Change는 가져오는 브랜치 쪽으로 표시됨. 선택 버튼을 쓸 때도 최종 파일이 의도한 내용인지 확인함. 모든 충돌 표시를 제거하고 파일을 저장한 뒤 해결 상태를 등록함.

```powershell
git status
git add README.md
git commit -m "문서 병합 충돌 해결"
git status
```

`git add`는 충돌 파일을 해결한 것으로 표시하고 `git commit`은 진행 중인 병합을 완료함. 최종 내용이 기존 `main`과 같더라도 두 이력을 연결하는 병합 커밋이 필요할 수 있음. 충돌을 해결하지 않은 상태에서 `pull`이나 `push`를 반복해도 병합이 완료되지는 않음.

## 진행 중인 병합을 중단하려면

```powershell
git merge --abort
```

진행 중인 병합을 중단하고 시작 전 상태로 돌아가려는 명령임. 병합 전에 미커밋 변경이 있으면 복구가 불완전할 수 있으므로 시작 전에 상태를 정리하는 편이 안전함. 다음에는 작업 커밋을 새로운 기준 뒤에 다시 적용하는 rebase를 비교함.
